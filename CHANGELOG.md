## [Unreleased]

### Added

- **Cargo workspace with four crates and a hard purity boundary.** The repository now builds as a single workspace holding `broom-core` (the engine), `broom-rules` (TOML rule packs), `broom-cli` (the `omnibroom` binary), and `broom-ffi` (the UniFFI surface). This split exists because Path B was locked on day one: one engine, four surfaces (CLI today, Tauri GUI, phone apps, and an agent wrapper later) all calling the same core, so the rules and verdicts can never drift between platforms. `broom-gui` is deliberately absent until Rung 7 earns it, and the crate graph enforces the load-bearing discipline from the vision doc: `broom-core` depends on jwalk, rayon, thiserror, and serde only, so no tokio, no subprocess spawning, and no TUI dependency can enter the engine by accident.

- **Parallel filesystem walker built on jwalk with rayon under it.** The engine walks every root in parallel, resolves file sizes during the walk, and sums matched directory subtrees lazily and in parallel afterward, so a scan over a tree that matches nothing pays only for the walk itself. Hidden entries are walked explicitly (`skip_hidden(false)`) because the caches this tool exists to judge are dot-directories like `.npm` and `.cache`, and jwalk skips them by default. Walk failures are capped warnings rather than hard errors: a full disk with permission corners is exactly the machine OmniBroom is for, so one unreadable directory can never abort a scan. Symlinks are not followed by default, because symlink loops hang walkers and a swept symlink target is always a surprise.

- **Verdict model with a reason on every finding.** `Verdict` is a three-state enum (`Safe`, `Risky`, `Never`) ordered by severity so that when multiple rules claim one path, the most severe verdict wins, and a finding without a reason cannot exist: the reason string is a mandatory field everywhere. The same reasoning serves `why`, where every rule that claims a path is shown with its verdict and its reason side by side. The product pitch is "ncdu shows sizes, OmniBroom shows consequences," and this is the data model that pitch requires.

- **Facts providers as injected traits, with docker, journalctl, and git implementations in the CLI.** The engine defines a `FactsProvider` trait and never learns what docker is; the CLI injects three implementations that shell out and translate tool output into `Fact` records that rules classify. This keeps the "no subprocess in the engine" rule true in the type system rather than by convention, and it means a surface without those tools (a phone build, a test) simply injects nothing and still works. Failures degrade to warnings: a machine with no docker daemon still gets every filesystem and journal finding.

- **Docker facts parsed from plain-text output because `--json` does not exist everywhere.** The provider probes the daemon once, then reads dangling images, per-builder buildx cache totals from `docker buildx du`, and dangling volumes. `docker system df --json` was rejected: docker 29.8.1 on the build machine returns `unknown flag: --json`, so parsing the human formats is the portable choice. One safety detail is load-bearing: `docker images --filter dangling=true` also lists untagged images that running containers still use (verified live: this machine's homepage and code-server both run on untagged images), so the provider cross-checks `docker ps -a` and excludes any image a container references before calling it safe.

- **Journalctl and git worktree facts.** `journalctl --disk-usage` runs with `LC_ALL=C` so the size line parses regardless of the user's locale, and both the modern one-line output ("Archived and active journals take up 207M") and the older two-line archived/system output are handled by summing every size found. The git provider walks the repo roots the scanner already discovered, reads `git worktree list --porcelain`, resolves the default branch through origin/HEAD with origin/main, origin/master, main, master as fallbacks, and emits a fact only for a linked worktree whose branch is provably merged (`merge-base --is-ancestor`) into that base. Detached worktrees and worktrees parked on the trunk itself are skipped rather than guessed at, and `GIT_TERMINAL_PROMPT=0` guarantees a scan can never block on a credential prompt.

- **TOML rule-pack schema with 15 built-in rules across four packs.** Rules are data, never code: the schema is a serde-derived TOML shape (id, category, verdict, reason, match, optional conditions) that the compiler turns into precompiled glob matchers at startup. The four built-in packs cover the v1 scope fence exactly: docker (dangling images safe, buildx cache safe, orphaned volumes risky), node (node_modules outside a worktree safe and inside risky, npm and pnpm caches, `_logs`, `_npx` all safe), git (merged-branch worktrees risky, because uncommitted files may still live there), and system (journal logs, `/tmp`, `*.wal`, and `*-wal` sidecars, all in the never class). The packs are compiled into the binary with `include_str!` so the bytes classified with are byte-identical to the files in `crates/broom-rules/packs/`.

- **Conditions on rules, which is how one pattern carries two verdicts.** A rule can require `inside_git_worktree = true` or `false`, so `node_modules` classifies as safe when it sits outside any checked-out project and risky when it belongs to one. The engine resolves the git context lazily and at most once per entry: entries no rule claims cost zero stat calls, because the condition check only runs after a pattern has already matched. This is the mechanism that keeps rule logic in TOML instead of hardcoded branches in the engine.

- **`omnibroom scan` with classified table output and `--json`.** The scan command prints a comfy-table of verdict, size, category, path, and reason sorted biggest-first, followed by a summary line that totals reclaimable versus locked bytes by verdict. `--json` emits the full serialized report (roots, findings with rule ids and origins, warnings, entry count, summary) on stdout while warnings still go to stderr, so piping into `jq` stays clean. `--no-facts` and `--max-depth` bound the work for scripts, and an indicatif spinner reports entries visited during long walks without leaking escape codes into redirected output.

- **`omnibroom sweep` with dry-run as the default and deletion gated behind `--yes`.** Running sweep with no flags prints the safe-to-delete table and an explicit "DRY RUN: nothing was deleted" line, and only `--yes` crosses into real deletion. The deletion policy lives in one place and is pinned by tests: only `Verdict::Safe` findings whose origin is the filesystem are ever removed; risky and never findings are not touched regardless of flags; safe facts findings (docker images, buildx cache, volumes, worktrees) are reported but not deleted, because deleting those needs provider-specific commands with their own safety rails, which is honest work for a later rung rather than something to fake now.

- **`omnibroom why <path>` explaining any verdict.** The command answers the product's central question for a single path: it reports existence, whether the path sits inside a git worktree (and which one), the verdict of record (the most severe claim among matching rules), and a table of every rule that fired with its id, category, origin (filesystem or facts provider), and reason. A path no rule claims comes back as explicitly unclassified rather than silently defaulted, so "OmniBroom has no opinion" is itself a first-class answer.

- **`broom-ffi` UniFFI stub that compiles today and generates no bindings yet.** The crate builds as cdylib plus rlib with `uniffi::setup_scaffolding!()` wired up and two exported functions (`scan_json`, `rule_ids_json`) using JSON-in/JSON-out so future shells never need Rust types across the boundary. Language bindings (Kotlin, Swift) are a `uniffi-bindgen` step that runs when the phone rung needs them; doing it before there is a consumer would be build cost with no user. The FFI stays synchronous because the engine is sync by design (no tokio in core), leaving threading to callers.

- **Quality gates from the first commit: rustfmt, clippy `-D warnings`, cargo-nextest with insta snapshots, and CI that runs all three in order.** The workspace holds 41 tests: engine tests on real tempfile fixtures (classification, nested-match collapsing, summaries, missing-root warnings), rule-pack tests including validation failures that must name the offending rule, sweep-policy tests that pin the safe-only deletion contract against regressions, and insta snapshot tests over verdict tables, `why` output, and the JSON report so any change to what users see arrives as a reviewed snapshot diff instead of a silent shift. The CI workflow runs fmt first (cheapest, most mechanical), then clippy with `-D warnings` (zero warnings, not zero errors), then nextest, which is the failure-fast ladder. CI carries no telemetry either: no coverage upload, no test analytics, no external dashboards.

- **A strong Rust `.gitignore`.** `target/`, editor directories and swap files, OS cruft, `.env` variants, release staging, and coverage output are all excluded from day one so the first commit contains only source, and `Cargo.lock` stays tracked because this workspace ships a binary.

### Changed

- **The binary is `omnibroom` with flat subcommands, not `omni broom`.** The original shape nested the commands under a two-word `omni broom` namespace, which read like a suite launcher for OmniSuite apps that do not exist yet and cost an extra word on every invocation. First real-machine use settled it: `omnibroom scan`, `omnibroom sweep`, and `omnibroom why` are one tab-completion away and say exactly what runs. If a suite launcher ever arrives it can wrap this binary; nothing in the engine knew the old name.

- **Size formatting settled on one decimal above bytes.** The formatter originally rounded values whose fractional part was near zero (so exactly 1024 read "1 KiB"), which was prettier but disagreed with its own test and would have made snapshot output depend on a rounding branch. It now prints one decimal everywhere above bytes ("1.0 KiB", "353.6 MiB"), which is predictable in snapshots and stable across refactors.

- **The walk outcome became a struct carrying warnings, not just entries.** The first walker returned only entries and silently dropped unreadable paths; that would have made a scan over a hostile filesystem look complete when it was not. Walk errors are now capped at ten individual warning lines plus a remainder count, keeping permission corners visible without letting a broken mount flood the output.

### Fixed

- **The system pack's WAL rules matched nothing as originally written.** They used the `name` match kind with patterns like `*.wal`, but name matching is an exact file-name comparison, so a file literally named `*.wal` was the only thing that could ever match. Both rules now use `path_glob` (`**/*.wal` and `**/*-wal`), and a snapshot test pins the never verdict on a real WAL file at depth so this cannot regress silently.

- **`journalctl` output with "takes up" was skipped by the size parser.** Older systemd prints "System journal takes up 300M" (with the "s") alongside the modern "Archived and active journals take up 207M", and the parser only split on "take up", so the system-journal line was dropped and under-reported. The parser now accepts both spellings and sums every size line, which is what makes the two-line output correct.

- **The rules fixture and its tests disagreed on where the orphan `node_modules` was.** The fixture created `loose_node_modules/pkg/index.js`, which no rule matches (the rule matches the name `node_modules` exactly), so the fixture produced no safe finding and the tests that looked for one failed. The fixture now creates a real `node_modules` at the root, and the assertions compare exact paths instead of suffixes so an in-worktree copy cannot be mistaken for the orphan.

- **`why` on a merged git worktree said "unclassified" while `scan` said "risky" for the same path.** Found during live verification against a real fixture repo, and it cut at the product's core promise: the tool that exists to explain verdicts declined to explain one it had just issued. The git provider skipped whichever worktree had the same path as the repo it was invoked on, which is the right skip for `scan` (invoked on the main checkout) and exactly the wrong skip for `why` (invoked with the linked worktree as its git context, so the worktree skipped itself and nothing matched). The skip rule is now positional: `git worktree list` always puts the main worktree first, so entry zero is the checkout that is never a removal candidate, no matter which worktree the provider was called from. `why` also now inherits facts from ancestor paths, the same containment rule the scan's collapse uses, so `why` on a file inside a risky worktree reports the worktree's fact instead of going quiet. Three regression tests pin all of it against a real git fixture: `scan` and `why` agree, files inside inherit, and the main checkout is never a finding.

### Security

- **No telemetry, anywhere, ever.** This is a brand position against mobile junk-cleaner apps and a locked decision: the binary makes no network calls of its own, ships no analytics, and the CI workflow deliberately uses no coverage-upload or test-analytics services. Facts providers shell out only to locally installed tools (docker, journalctl, git) on the user's own machine.

- **Deletion is gated behind an explicit `--yes` and a safe-only policy that tests enforce.** Dry-run is the default for `sweep`, `Never` and `Risky` findings are never deletable regardless of flags, and `GIT_TERMINAL_PROMPT=0` plus `LC_ALL=C` keep subprocesses from prompting or locale-shifting under a scan. The `why` command reports unclassified paths as unclassified instead of implying safety, so absence of a rule is never mistaken for permission.
